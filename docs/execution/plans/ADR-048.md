# Plan — ADR-048 Multi-Tenant Data Isolation

## Summary

Encode MerchantOS multi-tenant row-level isolation as an importable contract in `src/multi-tenant-isolation/`: shared DB/schema with mandatory `merchant_id` on tenant rows; store-scoped membership/inventory (and sales) via `store_id` under merchant (ADR-091); repository filters from trusted auth context; deny cross-tenant reads/updates by ID alone; platform-admin exception audited-only; unique/cache/topic keys tenant-scoped; PostgreSQL RLS noted as optional future hardening (not MVP). Assert helpers (`assertTenantMatch` etc.) + Vitest. Contract-only — no concrete domain tables or RLS policies.

## Database design

- No new concrete domain tables in this ADR (schema remains empty until domain ADRs)
- Tenant tables: `merchant_id UUID NOT NULL` mandatory
- Store-scoped operational tables: additional `store_id UUID NOT NULL` (membership, inventory/stock, sales) always under merchant
- Pure join / child tables may inherit merchant via parent — still queries filter trusted merchant context
- Platform/global tables: no `merchant_id`; role-gated (`platform_admin`)
- Unique indexes tenant-scoped `(merchant_id, …)`; store business keys include store scope where store-owned
- RLS: **deferred / optional later** — not enabled in MVP; application + repository filters are the primary control
- Align ADR-041 `TENANT_ISOLATION_EXPECTATIONS`, ADR-043 `TENANT_COLUMN`, ADR-045 `TENANT_FILTER` — deepen, do not fork column names
